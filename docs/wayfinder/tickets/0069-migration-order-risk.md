## Question

形态、旗标、tmp 结构定后，四个套件（站点 1660 行 / SOP 509 行 / reveal 366 行 / search 452 行）向 harness 迁移的次序与切法。迁移是本图唯一接近「施工」的决策面——但它仍是决策：切法决定风险形态，且迁移途中每条断言的牙不能丢（变异检验纪律，ADR-0009）。

要决策的面：

1. **横切还是纵切**：横切 = 按基建类别逐层迁移（先 Report/构建、再配置写入、再 DOM 装配，每层跨四个套件同改）；纵切 = 逐套件整体迁移（一个套件完全切到 harness 再下一个）。判据：横切每步可否独立验证（四套件同时改一半，中间态测试是否可跑）；纵切是否有「证明套件」——先迁最小的 SOP 套件（509 行、fixture 基建与站点套件耦合最少？需核实）还是先迁最热的站点套件（收益最早兑现、风险最高）。
2. **中间态的可运行性**：迁移期间旧副本与新 harness 并存——并存期多长、谁先删；「删旧」本身是否作为一个显式步骤（删掉即证明无隐藏依赖）还是自然消亡。
3. **断言完整性的保持**：迁移后每条既有断言必须仍有牙——迁移期如何执行变异检验（全量重跑「破坏→红→还原」成本 vs 抽样）；断言数量迁移前后是否可比对（如站点套件当前 87/87、reveal 23、search 41 类计数——收口批已有「测试类别计数同步文档」的先例，候选 12 的 6d626db）。
4. **与 CI 的关系**：迁移批的 CI 验证形态——本地 advisory vs CI 权威的既有分工（历图传承）是否足够；迁移批是否需要拆多个提交 / PR（每步一个可回退点）。

边界（不开票）：具体每个套件内部哪些行动、哪些不动——那是施工期细节，本票只定切法与次序；harness 形态未定的情况下本票阻塞（旗标与 tmp 决议是其输入）。

事实前提：架构评审候选①（各套件规模与重复分布）；既有套件当前断言计数（站点 87 / reveal 23 / search 41，以 `npm test` 与 python 套件实跑为准）；AGENTS.md §3（测试命令与 CI 门禁现状）。

**继承约束（0061 已决，2026-10-25）**：① bad/ 拆子根（`bad/products/` + `bad/sop/`）与每根卫生断言**已于 2026-10-25 提前落地**（先行批：TDD 四切片 + 双卫生断言变异检验 + 三套件全绿 site 159/159 · sop 104/104 · npm 64；落地时 0069 未开决，时序越位已由评审记录，本票剩余迁移面不受影响）；② harness 禁止存契约字面量（seam 之后只有机制）；③ 迁移期测试总数不减、每条仍有牙。详见 [0061 Resolution](0061-harness-boundary-infra-vs-contract.md)。
