## Question

结果呈现层深化与否及其契约（前提：0050 已决；渲染落点随 0050 定案的形态在本工单 Resolution 里收口）：

1. **要不要加深**：现状 fastsearch 结果 `li` 只渲染标题 + 链接（ADR-0010 快照）。候选加深项：命中摘要（`content` 字段即 .Summary 的 320 字符截断，投影已有）、标签（`tags`/`categories`，投影已有）——两者都在 index.json 六字段内，**不需要改投影，故不触发「改投影字段 = 三处同步」纪律**；命中高亮（要消费 fuse 的匹配区间，最接近引擎层，成本最高）。「不做」是合法答案——ADR-0010 指针原话是「若『结果可读性』成为真实需求，只改渲染层」，本工单就是审这个需求是否真实（对你自己、对运维 / SRE 读者的命令检索场景）。
2. **契约形状**：呈现层改动 = 改 `fastsearch.js` 文件头快照契约（ADR-0010 纪律：契约 + 代码 + 评审三件套，快照是现状升格的契约、不是设计文档）；快照要扩写哪些条款（渲染字段 / 空态 / 无结果态 / 高亮若做的匹配区间语义）。
3. **落点**：search 页结果列表 / 新入口的结果浮层（随 0050）；若 0050 选「跳转 search 页」则落点唯一，本工单只剩「加深与否 + 契约扩写」两问。

**推荐**：先验需求真实性——若你或目标读者会觉得「只看标题不够」（例：搜 `kubectl` 出来 5 篇标题相近的命令文），加摘要（投影内字段、成本最低）；高亮建议明确否决（动 fuse 结果消费，违背「只改渲染层」的边界）；标签价值低（结果少时是噪音）。若需求不真实，显式维持现状也是收口。一次一问，先给推荐答案。
